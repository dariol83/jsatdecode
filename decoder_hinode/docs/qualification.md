# Hinode verification

## Automated checks

From the repository root with JDK 21 or later:

```powershell
mvn -pl decoder_hinode -am verify
```

The build runs the self-contained `HinodeTest` main through exec-maven-plugin.
Surefire's zero-JUnit-tests message does not mean these checks are skipped.
The suite covers:

- ServiceLoader discovery, runtime-shaped decoder configuration including
  `type`, unknown and mismatched settings, and lifecycle/failure behavior.
- All ten mandatory status keys, descriptors and value types across lifecycle
  states, good/bad/total accounting, frame counter aliases and offset gating.
- The CCSDS PN prefix and independent randomizer agreement, arbitrary bit
  alignment, correction of 16 errors per RS interleave, rejection beyond RS
  capability, and an independent convolutional encoder through Viterbi/ASM/PN/RS.
- Enabled DC rejection, impulse response, 32766-input-sample group delay,
  independent I/Q history, raw-bit bypass, strict boolean parsing and receiver
  switch wiring.
- Identical timing symbols across 4096- and 137-sample input blocks, in enabled
  and bypassed DC modes, and generated residual-carrier PM reception.
- Positive and negative carrier offsets through the complete decoder, including
  lock-dependent Hz reporting and NaN before start, during search and after stop
  or failure.

These generated checks require neither mission recordings nor SDR hardware.
Their results do not establish byte equivalence to an external receiver or live
reception performance.

## Recording and desktop verification

`HinodeQualification` accepts a 90-second float stereo I/Q WAV at 500 kS/s and an expected
file containing concatenated 892-byte transfer frames. No mission recording or
expected frame file is tracked. Run from the repository root after the build:

```powershell
java -cp 'decoder_hinode/target/test-classes;decoder_hinode/target/classes;decoder_hinode/target/lib/*' eu.dariolucia.jsatdecode.hinode.HinodeQualification reference.wav expected-frames.bin
```

The harness runs twice with UI OFF and once with the actual desktop UI ON,
including RF/baseband FFT, constellation and generic monitoring. It rejects
headless fallback as desktop verification. Each run must match the supplied
expected bytes, count and order, exceed 2x real time, and contain more than 300
frames. Retention is bounded to 10000 frames; source failures and timeouts
propagate. An expected file generated by the same Java receiver establishes
reproducibility, while an independently established expected file supports an
external byte comparison.

Record recording/output hashes, hardware/JVM, console output and monitoring/FEC
results alongside the run. Inspect lock acquisition, taps, EOF and UI behavior.
Repeated measured runs are needed to assess UI throughput overhead.

The optional generated-signal profiling main is:

```powershell
java -cp 'decoder_hinode/target/test-classes;decoder_hinode/target/classes;decoder_hinode/target/lib/*' eu.dariolucia.jsatdecode.hinode.HinodeSyntheticSignal
```

Hardware acquisition, RF lock/loss/recovery and source shutdown require the
relevant live SDR environment. Synthetic or recorded playback alone does not
verify those hardware behaviors.
